# 01 — git 行為 ↔ Minecraft 世界對照

先把名詞對齊。之後所有文件都用這張表的說法。

## 名詞

| git | Minecraft 裡的對應 | 說明 |
|---|---|---|
| repository | 一個被追蹤的世界（或世界中的一塊區域）及其全部歷史 | 歷史存在世界資料夾**外面**（例如 `<server>/.worldgit/<world>/`），避免 MC 自己的存檔／備份工具碰到它。 |
| working tree | **正在被遊玩的那個世界**（活的世界） | 玩家在裡面放方塊就等於在改 working tree。 |
| blob | 一個 chunk section（16×16×16）的正規化內容；一個 chunk 的實體列表（含所有生物，不含玩家） | 詳見 [02](02-data-model.md)。 |
| tree | 維度 → region(32×32 chunk) → chunk → section 的階層 | 沒變的子樹直接共用雜湊，所以 commit 很便宜。 |
| commit | **存檔點**：某一刻整個被追蹤範圍的快照 + 作者 + 訊息 + MC 版本 | 作者可以是多位（這段時間內改過方塊的玩家）。 |
| HEAD | 活的世界目前「站在」哪個 commit / 分支上 | 顯示在 scoreboard / bossbar / `/wg status`。 |
| branch | 一條平行時空 | 例如 `main`、`castle-v2`、`alice/redstone-test`。 |
| index / staging area | 大多情況**省略**：commit 時直接收整個世界的變動 | 進階用法：`/wg add <選取範圍>` 只把某區域的變動放進下一個 commit（「我只想存城堡，不想存旁邊的實驗」）。 |
| .gitignore | **`.wgignore`**：放在 repo 根目錄、被版本控制的排除規則 | 可依維度、座標範圍、實體類型、NBT 欄位排除，支援 `!` 加回。預設什麼都不排除。詳見 [02](02-data-model.md) §5。 |
| remote | Hub 上的同名 repo 或另一台伺服器 | |
| conflict | 兩個分支自共同祖先以來**都改了同一格方塊（或同一個實體）且結果不同** | 以「衝突區域」呈現，而非一格一格。 |

## 指令對照

遊戲內前綴暫定 `/wg`，CLI 暫定 `wgit`。「必要度」是我對 MC 使用情境的判斷：★★★ = MVP 必備，★★ = 第二階段，★ = 有空再說 / 可能不做。

### 存檔點與歷史

| git | MC 行為 | 必要度 | 備註 |
|---|---|---|---|
| `init` | 開始追蹤這個世界（可指定只追蹤某個範圍） | ★★★ | 第一次 init 等於做一次完整快照，較慢，之後都是增量。 |
| `status` | 列出自上一個存檔點以來**哪些 chunk 被改過**、誰改的 | ★★★ | 遊戲內可以用粒子/外框把變動 chunk 標出來。 |
| `commit -m` | 手動存檔點 | ★★★ | 另有自動策略：登出時、每 N 分鐘、伺服器關閉前。自動 commit 可標記為 `auto`，在 log 中可折疊。 |
| `commit --amend` | 把最近的變動併進上一個存檔點 | ★★ | 自動 commit 很多時很好用：`/wg squash` 把一串 auto commit 壓成一個。 |
| `log` | 存檔點時間軸（書本 GUI / 網頁） | ★★★ | 網頁端每個 commit 附一張俯視縮圖。 |
| `show <commit>` | 顯示該存檔點改了什麼（變動區域外框 + 統計） | ★★ | |
| `tag` | 里程碑：「v1.0 開幕版」「比賽提交版」 | ★★ | Hub 上 tag = 可下載的 release（世界 zip）。 |
| `blame` | **這格方塊是哪個存檔點、誰放的** | ★ | 粒度是 commit 級，資料來自 WorldGit 自己的作者追蹤（見 [04](04-commit-and-status.md) §2）。不整合 CoreProtect（已決定）。 |
| `bisect` | 二分搜尋「哪個存檔點開始紅石壞了」 | ★ | 做起來其實不難（就是反覆 checkout），但需求小。 |

### 切換與復原（痛點 1）

| git | MC 行為 | 必要度 | 備註 |
|---|---|---|---|
| `switch <branch>` / `checkout <commit>` | **原地**把活的世界換成目標時間點：只重寫兩者之間有差的 section | ★★★ | 詳見 [05](05-switch-restore.md)。切換前若有未存檔變動 → 要求先 commit 或自動 stash。 |
| `switch -c <branch>` | 從現在這一刻開一條新時空 | ★★★ | 開分支不需要複製任何方塊資料，只是一個指標。 |
| `restore --source <commit> -- <區域>` | **只把某個區域**還原成某個存檔點 | ★★★ | 這其實是最常用的「復原」：「我的房子回到昨天，但別人的東西不要動」。用 WorldEdit 選取或 chunk 範圍指定。 |
| `reset --hard` | 丟掉目前所有未存檔變動，回到 HEAD | ★★★ | 等於「讀檔」。 |
| `revert <commit>` | 產生一個「反向」存檔點，撤銷某次改動但保留之後的歷史 | ★★ | 多人伺服器上比 reset 安全：不改寫歷史。反向套用時若後續又改過同一格 → 走衝突流程。 |
| `stash` | 暫存目前未存檔的變動，切換後再拿回來 | ★★ | 內部實作就是一個隱藏的 commit。 |
| `worktree add` | 為另一個分支開一個**系統託管的暫時世界**，用於並排比較或多人同時在不同分支工作 | ★★ | 解決「世界越開越多」：worktree 世界名稱固定（`world@branch`）、不出現在一般世界列表、合併後自動刪除。 |

### 合併與協作（痛點 2）

| git | MC 行為 | 必要度 | 備註 |
|---|---|---|---|
| `diff` | 兩個時間點/分支的差異：新增（綠）、移除（紅）、修改（黃）方塊外框 | ★★★ | 遊戲內用 display entity 描邊；網頁端 3D。 |
| `merge <branch>` | 三方合併到目前分支 | ★★★ | 無衝突自動完成；有衝突 → 世界進入「合併中」狀態，見 [06](06-diff-merge.md)。 |
| `merge --abort` | 放棄合併，世界回到合併前 | ★★★ | 因為合併前狀態就是 HEAD，必定可以乾淨回去。 |
| `cherry-pick <commit>` | 把「某一次改動」（例如一棟建築）套到另一個分支 | ★★ | 本質是對該 commit 的 diff 做三方合併。 |
| `rebase` | 把自己的一串存檔點「搬」到主線最新版之後 | ★ | 對世界來說價值低，log 好不好看不太重要。可以不做。 |
| Pull Request | Hub 上的「請求把我的分支合進主線」+ 3D diff 審閱 + 留言（可釘在座標上） | ★★ | 見 [07](07-remote-hub.md)。 |

### 雲端（痛點 4）

| git | MC 行為 | 必要度 | 備註 |
|---|---|---|---|
| `remote add` | 綁定 Hub repo 或另一台伺服器 | ★★ | |
| `push` / `fetch` / `pull` | 只傳對方沒有的物件（section blob），所以通常很小 | ★★ | |
| `clone` | 從 Hub 下載某分支並**生成可以直接開的世界資料夾** | ★★ | 單人玩家拿到就能開。 |
| `clone --filter / sparse-checkout` | **只拉某個區域**（例如大伺服器裡你負責的那一區） | ★ | 大地圖（數十 GB）協作時很關鍵，但實作複雜。 |

### 維護

| git | MC 行為 | 必要度 |
|---|---|---|
| `gc` / `prune` | 清掉沒被任何分支引用的物件、打包壓縮 | ★★ |
| `hooks` | 事件鉤子：commit 前（例如檢查範圍內沒有違禁方塊）、合併後（通知 Discord） | ★ |
| `submodule` | 「預製件庫」：把共用的建築模組當成子 repo 引用 | ★（概念有趣，先不做） |

## MC 特有、git 沒有的東西

這些在 git 裡沒有對應，但世界版本控制一定會遇到：

1. **MC 版本升級（DataVersion）**：舊 commit 是 1.21 的格式，現在伺服器是 26.x。checkout 舊存檔點時必須先過 DataFixer 升級；合併兩個不同版本的分支前，要先把兩邊都升級到同一版。每個 commit 都要記錄 DataVersion。
2. **衍生資料**：光照、heightmap、POI 等可以從方塊重新計算，不應該進版本控制（會造成假 diff），寫回世界時讓遊戲重算。
3. **會自己變的東西**：作物生長、水流、生物走動、熔爐燒東西。它們會讓 `status` 永遠不乾淨 → 需要正規化與 `.wgignore` 規則（見 [02](02-data-model.md) §5、§8）。
4. **「活的」工作目錄**：git 的檔案在你改它時不會自己動；世界在 checkout 當下可能有玩家站在裡面、chunk 正被載入。這是本專案最大的工程難點（見 [05](05-switch-restore.md)）。
